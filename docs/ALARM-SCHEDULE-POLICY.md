# 告警规则生效时段

2026-10-19。源码与隔离验证已完成；不代表现网部署或浏览器端到端验收。

## 用户操作

告警分析 → 新建或编辑监控规则 → 用途与保存 → 生效时段。

- 每天全天：保持现有规则行为。
- 每周指定时段：选择规则时区、开始日和起止时间。可添加至多 28 个时段；一行可选择多天。
- “这几天全天”明确表示 00:00–24:00。普通输入开始和结束相同会阻止保存，不能隐式当作全天。
- 结束早于开始表示次日结束，例如周日 22:00–06:00 包含周一凌晨。界面显示“次日结束”。
- 切换全天与每周模式时，编辑器保留尚未保存的每周设置。保存前摘要、规则列表和再次编辑均显示规则时区与时段。
- 初次选择每周模式时以浏览器时区作为可修改的建议，保存后固定使用选定时区，不随浏览器或设备时区变化。
- 空星期、无效时区、重叠时段（包括跨午夜及跨周的重叠）阻止保存。前端提示、Web 后端和告警服务分别验证。

## 协议与执行

参数库存储在监控器文档的 `schedule` 字段，沿用 PG 版本历史及原有幂等保存。无此字段的旧规则默认全天；明确传入 null、未知模式或额外字段不会降级为全天。

```json
{
  "mode": "weekly",
  "timezone": "Asia/Shanghai",
  "windows": [
    {"days": [1, 2, 3, 4, 5], "start": "22:00", "end": "06:00"}
  ]
}
```

`days` 是 ISO 星期，1 为周一，7 为周日。全天协议为 `{"mode":"always"}`。每周模式必须提供命名 IANA 时区，不接受纯数字偏移代替时区。起点包含、终点不包含。

PG 发布给各行为的执行快照包含相同 schedule。告警服务依据原始观测 `captured_at` 的绝对时间，在规则指定时区转换后判断；不使用消费时刻，积压或离线回放不会按当前钟表时间误触发。每周规则拒绝没有 UTC 或明确偏移的采集时间。

时段外不生成该规则的行为事实或告警。状态转换清除旧停留和穿越证据，并以 `schedule_ended` 结束旧活动；下一次生效重新开始活动。即使没有收到时段外的帧，也通过时段身份识别下一生效区间，不能连接两个区间的轨迹。相邻且无间隙的时段视作连续生效，包括周日跨周一，避免配置分段人为中断轨迹。

时段转换随输入观测推进。无新输入时，活动结束标记要等下一帧才能写入；记录的 ended_at 是这次后续观测时间，不声称精确测得断流期间的边界。停流生命周期与输入覆盖完善仍属待办。

夏令时按当地墙上钟表处理：不存在的本地小时没有观测；重复小时均可能生效，连续生效期间不单因时钟回拨而重开活动。跟踪与停留仍用同会话 PTS，不能以墙上时钟代替运动时间。

告警保留规则快照；行为事实以 rule_id/version 关联 PG 不可变规则历史。修改时段必须产生新版本，已经物化的事实、确认审计与故障恢复结果不随新时段改写。统计只反映实际记录，未生效时段及输入缺失不能当作完整监测下的零。
