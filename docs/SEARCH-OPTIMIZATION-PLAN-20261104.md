# 文搜优化方案（2026-11-04）

单一路径，唯一的分支是第 2 步的 A/B 门。状态：方案阶段；未提交、未部署。

## 0. 要解决的问题
1. 场景图被**压扁成 256×256**（不保长宽比）。后门 8K 全景宽 7680 像素压到 256，一个 100 像素宽的人只剩约 3 像素。
2. 中文查询的召回**没有验证过**（板上只测过英文 Flickr 生活照与中文向量的浮点一致性）。
3. 通道变多后的采样负载与降速行为**没有实测**。

## 1. 已查清的基线（只读检查）
- 搜索模型是 SigLIP2 base 256（768 维），索引是自写的**精确余弦检索**（内存），不用外部向量数据库，不存在近似检索的召回损失。
- 采样触发：目标轨迹（每条最多 8 槽，每秒最多一次提议）+ 整帧场景（有活动 10 秒，静态 60 秒，变化 3 秒）。
- 容量不足时，系统**不丢样本**：采样记为"延期、覆盖账本欠着"，下一帧再试（`SearchSamplingOffer::deferred`），已经是优雅降级。
- 当前只配置了 1 个采样通道（后门 8K 全景 AI 输出），`producer_queue=1`，执行线程 2、队列 8；跨通道公平性目前无法观察。
- 索引分片：2026-11-02、2026-11-03 各约 1 万条，每片 34 到 35 MB，状态 ready。
- 板上有真实录像：`/mnt/ainvr-ssd/recordings`，129 段、30 GB，2026-10-11 到 11-03，含后门 8K 通道（c79a9337…）和另一通道（3a17d1f4…）。
- **未知**：真实每秒落库速率；`Usage()` 的 `offer_status`、`deferred_offers` 计数现在是什么；中文召回；切块收益。

## 2. 路径
### 第 1 步：测基线（只读，不影响生产）
- 读 ai-service 的 `Usage()` 计数在哪里暴露，取一次现值，判断当前是否容量受限。
- 用当前配置读搜索服务容量接口的条数/字节（需要服务调用密钥，只在内存里用，不落盘不外传）。
- 结果决定 `producer_queue` 是否值得调高。**不满足"容量受限"就不改。**

### 第 2 步：切块 A/B（离线，不影响生产）— 唯一的门
- **取帧**：从真实录像按通道、按白天/夜间/逆光分层，有界抽取（目标 150 到 300 帧），保存原始分辨率。
- **三种方案**，用同一组已部署的 SigLIP2 HBM 嵌入，预处理与生产一致（缩放、归一化）：
  - A：整帧压扁（现状）。
  - B：3 个重叠方块 + 整帧，检索取最高分。
  - C：仅 3 个重叠方块，取最高分。
- **查询集**：40 到 60 条中文查询，覆盖人员/颜色/携带物/车辆/小目标/无匹配。
- **标签**：4B 复审模型的教师标签，**明确记为教师标签**，另抽 50 对由人工判断，一致率 ≥ 80% 才采信教师标签。教师标签看的是降采样整帧，可能漏小目标，会低估切块收益，所以人工抽检必须包含小目标样本。
- **通过标准（运行前写定，不事后改）**：B 相对 A，Recall@10 提升 ≥ 10 个百分点；无匹配查询的误返回率增加 ≤ 5 个百分点；人工抽检不出现切块更差的系统性证据。任一不满足则**不做切块**，把结论写进文档后终止。

### 第 3 步：切块上线（仅第 2 步通过）
1. 先读 `sample_contract` 与索引聚合，在"一个样本多个向量"和"每块一个独立样本"两种做法里选。后者会破坏"一个候选、一个回执、一个覆盖令牌"的不变量，默认倾向前者。
2. 方块在现有 GLES 路径上渲染（`gles_preprocess`），不用 CPU。
3. 预处理合约变了就是新的嵌入空间，**必须清空并重积累搜索历史**，走 `search_fresh_model_cutover` 工具，遵守已知坑（`setsid nohup`、`AINVR_FRESH_READY_TIMEOUT_MS=600000`、备份目录名须符合 `\d{8}T\d{6}Z(-\d+)?`）。
4. 搜索结果显示命中的是哪一块，并高亮对应区域。
5. 阈值按"最高分"重新标定。
6. 保留回滚备份；先在隔离夹具上验证，再换生产。

### 第 4 步：小项
- `producer_queue`：依第 1 步结论再定。
- 搜索相似度默认值：现为 0.25，而 SigLIP 实测分数只有 0.06 到 0.14，默认值会让搜索全空。**这会推翻你之前明确选的值，需要你决定**。
- 自适应预算（全局每秒嵌入预算、通道间公平分配）：单通道下无法验证，且系统已有延期机制。**多通道真正接入之前再做**，验收用假时钟的多源单测加推流实测。

- 不换嵌入模型（Qwen3-VL-Embedding 已验证过但每张 1.5 秒，且需整库重积累）。

## 7. A/B 判定的精确定义（在看到任何结果之前写定）
**数据**：真实录像（`/mnt/ainvr-ssd/recordings`，129 段，2 个通道，均为同一机位的鱼眼 1080p 画面）每段取 t=12 s、40 s 两帧。
**局限**：单一机位、白天为主、画面里的人多数穿蓝色工作服；结论不能外推到其他机位、夜间或 8K 全景通道。
**查询**：50 条中文（`queries.json`），其中 18 条预期无匹配（只是先验，相关性只看标签）。
**视图**（SigLIP2 base 256，预处理同生产：RGB、INTER_AREA、(x/255−0.5)/0.5）：
- A 整帧压扁（现状）；A2 整帧保长宽比补成方形；
- 3 个方块（边长 = 帧高，起点 0、居中、右对齐，重叠）；
- B = max(整帧压扁, 左, 中, 右)；B2 = max(A2, 左, 中, 右)；C = max(左, 中, 右)。
**池化标注**：每个方法每条查询取前 5 帧，并集送 4B 复审（告警类型"查询"，描述"画面中存在：<查询>"，整帧 896×448 补边，`p_yes ≥ 0.5` 为相关）。这是标准的池化相关性判断；教师只看降采样整帧，会漏掉小目标，从而**低估**切块收益。
**指标**：
- 有至少 3 个相关帧的查询算"正例查询"，宏平均 Recall@10 与 P@10（相对于池内相关帧）；
- 无匹配误返回率：对每个方法取全局阈值 t，使其池内相关对的召回为 50%，然后统计"池内无相关帧的查询"里有多少条仍有结果得分 ≥ t。
**通过标准（全部满足才做切块）**：
1. 宏平均 Recall@10：B（或 B2）≥ A + 0.10（绝对值）；
2. 无匹配误返回率：B（或 B2）≤ A + 0.05；
3. 人工复核 50 对与教师标签一致率 ≥ 80%；
4. 比较对象还包括 A2：如果 A2 已经拿到 B 的大部分收益（B 相对 A2 的 Recall@10 提升 < 0.05），则只需要把"压扁"改成"补边"，不做切块。
任一不满足则不做切块，结论写入本文件后终止。

## 10. 用户决定：文搜与检测框无关（2026-11-04）
**用户反复强调的要点**
1. 文搜的本质是"画面与文字对齐"，不是"检测目标检索"；不考虑检测框，也不假定检测框和要搜的东西有关（检测到的是包或人脸，客户要搜粉色围巾、电缆，位置可能离框很远）。
2. 不同通道的检测模型不同（80 类、人脸等），框差异很大，搜索结果不能随之漂移。
3. 步行街等人多的场景，检测框遍布全图，等于要处理全图；成本应与画面有关而不是与目标数有关。
4. 画面是 2:1 或 16:9，不应压扁成方形：左、中、右各取一个带重叠的方块，各缩到 256×256，得到 3 个 768 维向量；搜索时文本向量与每个向量比，任一命中就列出。
5. 不必每帧都做；设目标，跑不过来时智能降速，多通道时自适应拉长抽帧间隔。
6. 搜索全部用中文，要在乎中文精度；方案要和顾问一起核对。

**决定**：基线层改为检测无关的画面层。检测框不再进入文搜。

**代码里对检测的依赖（已核对）**
- 目标路径：`reused_channel_worker.cpp` 对每个带轨迹的检测框调用 `OfferObject`，裁剪后压成 256×256。
- 场景路径：`scene.active = !result.detections.empty()`，即场景采样频率（有活动 10 秒 / 静态 60 秒）取决于"有没有检测框"，这是隐性耦合，必须去掉。
- 配置：控制台已有 `sampling.object` / `sampling.scene` 两个开关和四个间隔，关闭目标路径不需要改代码。
- 检索：场景样本在 `vector_index.hpp` 里每个样本自成一组，`rank_refine.hpp` 已有"同一场景相隔几秒的连续样本只留最好的一条"的近重复折叠，连续帧命中不会刷屏。

## 13. 目标裁剪图 A/B 结果与一条更正（2026-11-04）
615 张真实人物裁剪图、24 条人物属性查询、398 对 4B 教师标签（20 条正例查询）。按第 9 节登记的标准：
- 压扁（OS，现状）Recall@10 0.447，补边（OL）0.351，**OL − OS = −0.096**（95% 区间 −0.205 ~ +0.010）；R-precision（事后）OS 0.369、OL 0.301，**OL − OS = −0.068（区间 −0.123 ~ −0.012，显著更差）**。无匹配误返回率 OL 也不低于 OS。**登记标准未通过，目标裁剪图保持压扁，不改补边。**
- **更正我之前的说法**：我曾把"压扁"当成缺陷。SigLIP 系列（非 NaFlex 版本）的预训练和标准预处理本来就是把图直接缩放成方形，压扁对模型是"分布内"的，补边反而让主体更小、带入大片灰边。场景整帧的补边（A2）在场景 A/B 里也没有优于压扁（0.463 对 0.471）。**所以"保长宽比"不是改进方向，切块的价值只在分辨率（小目标），不在长宽比。**
- 局限：20 条正例查询，教师把裁剪图居中放在黑底 896×448 上，只代表这批同机位的人物裁剪。

## 14. 用户决定与重构原则（2026-11-04 晚）
**决定**：按"画面左中右三块（边长=短边，竖图为上中下）"改，上线由用户实测；历史数据可以清空。本方案在三块之外保留一个整帧向量（B 方法，R-precision 事后指标更好；"只有三块"事后指标低于现状）。每块照样压成 256×256 方形，不补边（补边在 A/B 中显著更差）。
**补充原则**：文搜与检测框、检测模型、检测类别、轨迹**完全无关**，整条逻辑理顺成两半：
- **建索引（图文对齐）**：帧 → 调度（时间间隔 + 嵌入变化探测 + 预算）→ 视图规划（整帧 + 沿长边的方块）→ 视觉编码 → 一个样本（一张 JPEG + 各视图向量）→ 入库。
- **文搜图**：中文查询 → 文本向量（缓存）→ 在每个样本的各视图向量上取最高分 → 时间/通道/授权过滤 → 近重复折叠 → 结果带"命中视图" → 可选大模型复核。
**已核对的耦合点（需要拆除）**

3. 场景频率取决于有无检测框：已用 `SearchSceneActive` 去掉（代码在仓库，未部署）。
4. 索引与结果聚合里的 object/track 分支、控制台"目标/场景"相关选项。
5. 注意：帧仍然来自 AI 通道的解码流（那是唯一解码帧的地方），"与检测无关"不等于"与 AI 通道无关"。

## 15. 切块 A/B 最终结果（补标"只有三块"后；2026-11-04 13:20）
**登记指标 Recall@10**（34 条正例查询，1165 对教师标签，含"只有三块"补标 31 对）：A（现状）0.464、A2（补边）0.457、B（三块+整帧）0.483、B2 0.489、**C（只有三块）0.473**。B−A = +0.019（95% 区间 −0.045 ~ +0.083），C−A = +0.009；**均未达登记的 +0.10，未通过**。局部查询（30 条）上 A 0.484、B 0.482、C 0.461 持平；整图查询（4 条）A 0.315、B 0.495、B2 0.579、C 0.568（样本小）。
**切块能否找回整帧看不到的小目标**（方块级重判，只对整帧教师判"否"的 295 对，每对 3 个方块）：整帧独有命中 282 对里 21 对（7.4%）在方块上其实有；切块独有命中 282 对里 22 对（7.8%）。两边几乎一样，**没有证据显示切块在这批 1080p 画面上找回了更多真目标**；含方块判断的精度 A 独有 0.535、B 独有 0.571。
**结论**：在 1080p 鱼眼、单一机位这批数据上，三块相对"整帧压成一个向量"没有可测量的召回提升；整图类查询可能有提升但样本只有 4 条。8K 源（每块缩得更多、小目标更小）没有数据。用户已决定按三块实现并上线实测；代价：每样本 4 个向量，内存可容纳样本数降到约 4.1 万；回到单向量需要再清库。
