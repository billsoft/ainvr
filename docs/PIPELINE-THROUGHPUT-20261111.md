# 双板取流与推理流水线优化验证（2026-11-11）

## 发布结论

本轮实现基于 `d10a5a0`，已在 .190（S100）和 .189（S100P）完成候选部署验证。二进制 SHA256：`3f572dee85c2ac266e3c0ee60b85a84ae2e7f4502defb69409c8de509ac42835`。最终发布基线以包含本文的 Git 提交和两板 `release-baseline.json` 记录为准。

保留的代码改动是网络读包与 VPU 输出回收解耦，不改变模型、检测阈值、跟踪匹配、触发器、计数规则、证据持久化、图像缩放或颜色转换。不能据本轮短时测试声称所有业务场景准确率不变或全天容量认证通过。

## 机制与边界

原 `StreamSource::Pump` 在 `MediaSource::Read()` 阻塞期间无法回收已经就绪的 VPU 输出。新增 `AsyncPacketReader` 用一个专用读线程和一个压缩包槽位承接网络等待，原线程每次最多等待 2ms，继续回收 VPU 输出。FIFO、PTS/DTS、压缩字节及 VPU 线程所有权保持原样；错误重新抛出，EOF 与暂时无包区分；停止先取消网络读再 join。

队列不累积，最多额外留一个压缩 AU（单 AU 仍受现有 64 MiB 校验上限约束），不会增加模型副本或像素队列。不是端到端零拷贝。PYM/GLES/JPU/VPU 沿用现有分工，没有为了提高某个利用率而强行更换预处理算法。

## 测试条件与结果

受控源为 SSD 上现有的 675 秒、1920×1080、25 FPS H.264 视频，以 `-re -c copy` 经隔离 SRS 提供；多路为独立取流/解码同一视频。测试通道关闭识别历史和衍生视频输出，没有新建业务告警绑定，后台业务服务保持运行。混合负载是一次不写告警库的真实复核模型调用，不是完整多帧/多视图审核链路。

帧率按推理计数增量/单调时钟窗口计算；BPU 为采样均值。多路观察窗口约 130–135 秒，单路约 60–62 秒，均在创建完成后等待 20 秒开始记录。

## 未保留的试验与测量修正

- 190 优化前八路曾触发保守的 600 MiB 停止线，原通道恢复。后续为观察边界使用384 MiB硬停止线；不同停止线不能当作内存优化的证据。
- 检测优先级64 + 复核提交份额10%：八路约2.822–2.830 FPS，复核约27.38s，接近30s执行超时；没有保留。
- 检测优先级64 + 原复核份额40%：复核约7.02s，八路约2.768 FPS，最低可用内存361.8 MiB触发停止；没有保留。
- 最终两板检测SDK优先级保持原值0，复核份额恢复/保持40%。正常混合测试同一复核样本在190约7.30s、189约5.49s完成，分数均为0.43012932353053446；这是固定样本一致性，不是准确率验证。
- 旧版单路探针5秒一次超过30帧结果缓存覆盖范围，跨轮拼接产生的“3.52秒间断”是探针缺口，不是已证明的真实断轨；已在 `one-before-summary.json` 将该项标为无效。候选单路改为约1.33秒采样；完整观测检查为true。FPS计数增量不受这个问题影响。

## 当前原输入的限制

原 `live/test-input` 发布端为 `192.168.100.182`。独立读流曾观察到显示顺序中33/34ms和100ms间隔并存，400包窗口约23.8帧/源秒。该缺口在AI推理前已存在，但尚未证明是发布端还是中间链路造成。没有登录或修改182。原输入与完整25 FPS测试源不可混为同一测试条件，也不能通过复制画面填补缺失证据。

## 固化的容量设置

- 190 原活动通道上限是2，本轮改为8，并启用既有、已通过字节/PTS合同测试的 `AINVR_AI_REFERENCE_DECODE=1`。该选项仅对满足条件的低速H.264非参考帧生效，当前15 FPS通道不启用筛选。
- 189 活动通道上限设为16，保留原参考帧解码选项。
- 模板：`deploy-package/s100-detection-capacity.conf`、`deploy-package/s100p-detection-capacity.conf`。安装到对应板 `/etc/systemd/system/ainvr-ai.service.d/70-ainvr-detection-capacity.conf` 后 daemon-reload/restart。
- 没有扩大已有AU字节预算。开启多路衍生输出仍需单独通过字节准入和容量验证，不能按“16个检测通道”宣称“16路全功能录像/输出/复核认证”。
