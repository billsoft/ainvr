## 4. 文本塔 ION 优化（int8 表与裁词表）

ION 大头不是 Transformer（权重本来就是 int8），而是词嵌入表：HBM 里查表数据按编译中间文件（BC）的 **2 倍**存放，所以 int16 表在 HBM 里占 4 字节/元素。把每个 `Gather` 的表输入设为 int8（`node_config` 的 `input0`）后占 2 字节/元素；位置嵌入保持原精度，不量化。受控实验：3.2 万 × 768 的表，int16 → HBM 93.9 MB，int8 → 47.0 MB。

| 文本塔 | 档位 | HBM | ION | 延迟 | 对原词表浮点余弦 |
|---|---|---:|---:|---:|---|
| so400m | 基线（int16 表） | 1583 MB | 1522 MB | 44.0 ms | 0.9938（最低 0.969） |
| so400m | **完整词表 + int8 表** | 1006 MB | 972 MB（−36%） | 27.4 ms | 0.9936（最低 0.987） |
| so400m | 裁词表 + int8 表 | 505 MB | 493 MB（−68%） | 16.0 ms | 中文 0.9932；英文 0.878 |
| SigLIP2-base | 基线（int16 表） | 879 MB | 850 MB | 22.2 ms | 0.9990（最低 0.997） |
| SigLIP2-base | **完整词表 + int8 表** | 485 MB | 475 MB（−44%） | 13.5 ms | 0.9984（最低 0.996） |
| SigLIP2-base | 裁词表 + int8 表 | 142 MB | 147 MB（−83%） | 5.6 ms | 中文 0.9982；英文 0.882 |

结论：
- **int8 表几乎无损**（对原词表浮点的余弦只低 0.0002–0.0006），ION 降 36–44%，延迟也降（查表受带宽限制）。这一档可以直接当默认。
- **裁词表**把词表限制到 ≤32768 行，只用一个 `Gather`，ION 再降一半以上；但取舍是**中英文**：中文保留全部 CJK 词片（SigLIP 2.16 万 / Gemma 2.38 万）加高频词片后，中文提示语余弦 0.993–0.998，与完整词表基本一致；英文常见词在大词表里排得靠后（`jacket` id 12350、`parking` 12175），32768 行装完中文后只剩约 5 千行给英文，被拆成碎片，端到端 Top-10 重合 61.7%。不能因此把它当默认，只适合明确只做中文检索的场景。
- 如果两者都要，可以放宽到多片（比如 10 万行），ION 介于两档之间，这一档**没有做**。
- 另一个非预期收获：裁剪后 so400m 文本塔只剩 493 MB，可以与 Qwen3-VL 的剩余 ION 余量一起评估是否能同时常驻，需要按板上 ION 规则（共同锁 + 静态预算 + 加载后试分配）实测，**我没有测**。

逐项耗时、通过/未通过表见交付包 `README.md` 第 4、5 节。

## 5. 这次踩到并解决的问题（可复用）

1. **词嵌入 Gather 的 BPU 上限**：`hbir.index` 要求被选维度 ≤ 32768，SigLIP 词表是 25 万，整张表会落 CPU。做法：把嵌入表切成 8 片（每片 ≤ 31250 行），每片用夹取后的局部下标取行，再乘 0/1 成员掩码求和。与整表查找逐位相同，保留全词表。剩下落 CPU 的只有对 64 个 token id 的整型 `Clip/Equal/Sub/cast_type`。审计脚本只放行"输入全为整型"的算子，任何浮点/神经算子落 CPU 都拒收。
2. **残差流的巨型激活**：文本塔通道 556 在 `<pad>` 位置达 ~370–440，内容 token 只有 ~0.2。HMCT 默认把 LayerNorm 拆成定点链，方差只有一个量化范围，内容 token 的归一化直接算错。**把 `LayerNormalization` 设成 float16 会让它以 `hbtl.call` 落 CPU，属于神经回退，不可用**（bfloat16/float32 走 HMCT 同一条"保留原生 LayerNorm"分支，未单独实测）。 做法：先按每个 token 的最大绝对值预缩放再算均值/方差（LayerNorm 对正的逐 token 缩放不变）。
3. **GELU(tanh) 的立方项**：`x + 0.044715x³` 在离群通道上把 `tanh` 的输入范围撑到 12.6 万。|x|>8 时 tanh 已饱和，把参数夹在 ±8 内无损，范围降到 ~25。
4. 以上两项叠加，文本塔 PTQ 仿真余弦从 0.58 升到 0.9994。只修其中一项都不够（单修 GELU 0.64，单修 LayerNorm 0.58）。
5. **诊断办法**：`text_quant_info.json` 里有逐节点余弦，找"第一个变坏的节点"比看最终指标快得多；PTQ 仿真（`ptq.onnx` 用 ORT + HMCT 自定义算子）与 HBM 结果一致，所以量化问题不用编译就能发现。
6. **ReID**：int8 + max 校准会把 OSNet-AIN 毁掉（余弦 0.36，仿真同样如此）；int16 + max 为 0.997。`kl` 校准在 PC 上极慢，已放弃。
7. **内存**：2.8 GB 的浮点文本塔量化峰值约 19 GB，容器上限要 ≥ 26 GB，且不能与别的大任务并行，否则被 OOM 静默杀掉（状态文件停在 `quantizing`）。`docker inspect` 的 `OOMKilled` 是粘性标记，不能当实时信号。HMCT 会把 `text_ptq_model.onnx` 存盘，被杀或 `onnx.save` 超 2 GB 报错时可用 `--resume-ptq` 续做，不用重新校准。
8. **脚本写法**：`pkill -f` 会匹配到自己的命令行；Windows 上 `sleep` 轮询被禁，改用监视器。

## 6. 已知局限

- **与 Qwen3-VL 同时常驻（2026-10-28 现网实测，详见交付包 README 第 8 节）**：Qwen 5459 MiB + ai-service 198 MiB 常驻时，默认的 so400m 文本塔（972 MiB）单独加载成功、512 MiB 试分配通过（剩余约 1058 MiB）；**但 so400m 文本塔 + so400m 视觉塔（共 1497 MiB）试分配失败（剩约 525 MiB），不能同时常驻**；so400m 裁词表文本塔 + 视觉塔、SigLIP2 整对都可以。**规程层面仍不放行**：静态预算规则下默认档差 73 MiB（899 对 972），且 `llm-service` 持有排他锁、登记表为 `exclusive_large_model`，要让文搜服务合法共存必须先扩展规程。我没有改任何规程、配置或服务。
- SigLIP2-base 视觉塔精度偏低（0.984），误差来自 12 个块逐层累积（约 1e-3/块）；试过夹取 softmax 无改善，没有继续深挖。
- 校准/评测图来自同一机位，评测是同机位异时段，不是独立视频；文本语料是按模板生成的监控提示语，语义覆盖有限。余弦和重合率只说明"板上结果像浮点"，**不是检索准确率，G1 仍需按设计文档用标注集验收**。
- ReID 只用 256 张同机位裁剪验证，跨机位泛化没测；OSNet-AIN 权重来自 LibreYOLO（MIT），训练数据集（MSMT17 等）原有研究用途条款；用户已于 2026-10-28 告知已付费获得授权（记录以用户说明为准，仓库内无授权文件）。
- **车牌：没有现成可用模型，也没有编译。** 官方 ModelZoo 的 LPRNet 只有 X5 版；公开检索未找到许可宽松、带中文的车牌检测+识别权重。可行路径是"车辆裁剪 → PP-OCRv6 det → rec"（两者均已实测，合计约 6 ms），但在真实车牌上的准确率**没有验证**。
- 文本分词器需要在服务侧实现：so400m 用 SentencePiece（小写 + 规范化，补齐到 64，pad=1），SigLIP2 用 Gemma 分词器（小写，pad=0，补齐到 64）。评测里的 token 是 HF 分词器生成的，C++ 实现需做逐条一致性测试。
- 未提交、未部署。
