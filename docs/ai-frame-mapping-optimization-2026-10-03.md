# 8K 解码帧 CUDA 映射优化（2026-10-03）

## 现场与定位

- 基线源码：`9ffc98a`；基线生产 AI SHA256：`0227f53b79419d44554cdd9a35e6aa219b879ce5296745fcd6fce7472c7704e1`。
- 真实源：7680×3840 H.265 codec12，约 30 FPS / 90–100 Mbps；模型 `yolo26x-face_fp16.engine`，640×640，目标 15 FPS。
- 同一二进制曾运行约 14.8 FPS，后降至约 11–12 FPS。映射均值约 25ms，模型推理约 43–47ms。
- 单次清理干净页缓存后，空闲内存由约 150MB 上升至约 7GB，映射仍约 24ms。不能据此认定缓存占满就是根因，也不设置周期性清缓存。
- 随后重建 AI 管线恢复到约 14.7–15 FPS，映射约 6.7–7.2ms。该步骤同时改变进程和缓冲区状态，不能单独证明内存碎片是根因。
- 独立程序分项计时：CUDA 注册约 6.7–6.9ms，EGL 创建约 0.13ms，其余单项不足 0.01ms。这确认正常状态下注册也是主要映射成本；尚未捕获异常 25ms 状态下的完整分项。

## 实现

1. 为单块、无父内存的 NVMM `GstMemory` 关联一份 EGL/CUDA 注册。身份依据是内存对象的生命周期，不是可能重用的地址或 fd。
2. 每帧仍持有 `GstSample`、映射描述符并查询当前 CUDA 帧。只有底层内存首次使用时注册；归还帧时不注销。
3. `GstMemory` 销毁时先注销 CUDA、解除 EGL，再由分配器释放 NVMM。注册期间保留 CUDA 主上下文，销毁回调显式切入该上下文。
4. 多内存或子分配内存保留原逐帧注册路径。所有者、CUDA 上下文、布局不符合预期时明确失败，交给现有恢复逻辑处理。
5. 调用方必须在释放视图前完成 GPU 工作。现有同步预处理、推理及截图下载满足这一约束；不能在未来改异步后直接提前归还帧。
6. 保留 `frame_map` 总耗时，增加 `map_context`、`map_gst`、`map_egl`、`map_register`、`map_get_frame` 五项 API 指标。每 900 次处理记录一次 `frame_mapping` 日志，包含复用/新注册次数及阶段均值。
7. 页面处理速度告警不再固定断言 GPU 满载，提示检查解码、映射与推理耗时。

未修改模型、精度、码率、目标 FPS、录像策略、功耗模式或系统内存参数。未将全幅处理改为降分辨率处理。

## 验证方法与边界

- 真实 8K 源首轮完整像素对照 321 帧无差异；因 60 秒执行预算未完成原计划 400 帧，不能记为整轮通过。
- 第二轮完成 200 帧：复用注册与新注册的完整像素相同，GPU 缩放 kernel 输出也相同，且确认发生缓存命中。
- 小型 NVMM 回归覆盖更新后的像素、重复映射、多线程读取、视图持有已释放外部引用的帧、视图移动、重复释放及多种尺寸分配重建。
- 真实管线回归覆盖 H.264/H.265、分辨率切换、重连、持帧期间重连和启停。
- 首轮通道测试的 100 秒上限不足以完成默认长压力循环，自动恢复旧服务；后续用 `AI_RECONNECT_CYCLES=3`、`AI_STOP_CYCLES=3` 完成有界回归。
- 这些检查不能替代多日运行观察。若出现花屏、读旧帧、映射错误或持续增长的显存/句柄，应保留日志并回滚，不能用自动重启掩盖。
