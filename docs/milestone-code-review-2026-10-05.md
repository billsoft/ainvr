## 问题记录

### 前端与控制台后端

#### WEB-01 · P1：PG 启动失败会使已设置的访问密码被当成“未设置”

- 位置：`srs-web-console/backend/src/app.ts:255,296`；`src/services/passwordCache.ts:43-67`；`src/app.ts:146`。
- 条件：密码已迁入 PG、旧 JSON 哈希已清除，后端启动时 PG 超过 12 次重试仍未就绪。
- 代码链：启动 catch 把 pgStore 置 null；密码缓存仅在存在 pgStore 且查询抛错时设置 pgBroken，null 情况回退空 JSON；鉴权钩子对空哈希直接放行。这不是用户主动关闭密码。
- 同时配置中心路由完全不注册，PG 后来恢复也不会重新初始化，持续 404 直到后端重启。
- 修复：区分“未配置 PG”和“已配置但不可用”；密码状态未知时显式拒绝管理请求。提供后台恢复初始化，或启动失败退出交给监督进程重试。

#### WEB-02 · P1：运行期 PG 故障的拒绝哨兵能被作为凭据使用

- 位置：`srs-web-console/backend/src/services/passwordCache.ts:26,63`；`src/app.ts:148-151`。
- 条件：PG 运行期读密码失败、本地旧哈希已清除。
- 代码链：密码缓存返回固定字符串表示不可用，app 却仍与请求头直接比较；调用者不需要求 SHA256 原像，固定哨兵不具备“拒绝所有请求”的能力。
- 后果：知道源码中的哨兵值的内网调用者可在此窗口绕过控制台访问密码。
- 修复：使用独立 unavailable 状态或异常并拒绝鉴权，不把错误状态编码为凭据字符串。

#### WEB-03 · P2：删除单张历史图的代理遗漏 PG 密钥来源

- 位置：`srs-web-console/backend/src/routes/aiProxy.ts:228-237`，对比同文件图片 GET 路由和 fwdWithId。
- 条件：AI API Key 由 PG secret 管理，settings.apiKey 为空或过时。
- 代码链：该 DELETE 路由没有传 opts.pgStore，只能使用旧 settings 密钥，其他历史接口能取到 PG 密钥。
- 后果：能查看历史，单条删除却返回 401。
- 修复：统一转发参数并补 pgStore；覆盖 PG secret 与 settings 不同的删除场景。

#### WEB-04 · P2：AI 启停专用超时未接入路由

- 位置：`srs-web-console/backend/src/routes/aiProxy.ts:149,153,190-191`。
- 代码链：声明了 15 秒停止、35 秒启动超时，但两条路由仍使用默认 8 秒。
- 条件及后果：模型初始化、归档收尾超过 8 秒时，页面报 502，远端操作却可能稍后成功。注释仍引用已淘汰的 Python 实现。
- 修复：接入实际超时并刷新最终状态；无法限定时长的操作使用操作状态查询，不以代理超时等同远端失败。

### 录像微服务

#### REC-01 · P2：配额删除没有保护仍在收尾的录像写入进程

- 位置：`recording-service/src/recorder/recording_pipeline.py:262-278`；`scanner.py:243-248`；`quota.py:28,101-118`；`playback_protection.py:34`。
- 代码链：切段时只关闭旧 writer 的 stdin，把进程放入 `_closing` 异步等待，马上允许新段；扫描器看见更新文件就将旧段视为 complete；配额只保护起始时间不足 60 秒的段及正在播放的段，并不知道 `_closing` 的文件。
- 条件：磁盘慢写导致旧 writer 尚未退出，旧段已超过一分钟，配置为滚动删除且达到配额、该段进入删除候选。长分段配置下“mtime 暂时不变”也不能证明 writer 已退出。
- 后果：可以 unlink 仍有写入者持有的文件，尚未完成的录像最终不可访问；进程继续写无链接 inode，空间也不一定立即释放。不能仅凭 complete 推断文件无人写入。
- 修复：维护当前及收尾 writer 的文件占用集合，成功退出后解除；scanner 和 quota 都检查占用，或使用临时文件名、写端退出后原子发布正式段。补慢收尾与配额清理交错的用例。

### AI 微服务

#### AI-01 · P2：配置“原子替换”没有保证持久化成功

- 位置：`ai-service/src/config/config_store.cpp:131-137`；`src/api/control_server.cpp:547-594`。
- 代码链：忽略文件 fsync 返回值；rename 后未 fsync 父目录，就返回配置保存成功。删除通道把 deletion_pending 写入此文件后即开始删除 Mongo 和 pending，最后删除配置项仍走同一写入函数。
- 条件及后果：发生延迟写入错误或替换后断电时，已报告成功的配置/删除标记可能未持久化；重启可能恢复旧通道、重新启动归档。文件名替换的原子性不等于掉电后的持久性。
- 修复：检查写入、fsync、close 错误；rename 后同步父目录，失败向调用者报告。用故障注入验证持久化失败不能报告删除完成。

### PostgreSQL 参数库

#### PG-01 · P2：提交后审计失败会把成功发布报告成失败

- 位置：`srs-web-console/backend/src/store/pgStore.ts:286-297`；`src/store/publishOrchestrator.ts:71`。
- 代码链：版本、快照、desired_version 已 COMMIT，随后通过连接池另写审计；此时审计失败进入 catch 再 ROLLBACK，无法撤销已提交事务，且异常阻断后续编排。
- 后果：界面收到失败，配置却已发布，拉取型服务仍可能应用；直接应用型服务可能没有收到下发，形成状态不一致。重新点击又创建新版本。
- 修复：发布审计与配置写入使用同一事务连接；提交后只处理应用结果，不再宣称事务回滚。需要记录后续应用审计时，将其失败与发布是否成功分开报告。
- 同类路径：upsertDocument、deleteDocument、setSecret 也是先变更后独立审计，修复时统一检查，避免只修发布入口。

### MongoDB 历史识别库

#### MDB-01 · P2：数据库删除失败被吞掉，接口报告不存在或成功删除零条

- 位置：`ai-service/src/output/snapshot_store.cpp:1778-1829,1857-1880`；`src/api/control_server.cpp:1014,1036-1042`。
- 代码链：DeleteOne 将未连接和异常转成 false，路由返回 404；DeleteRange/Clear 将未连接、Mongo 删除失败和异常全部转成 0，路由返回 HTTP 200。
- 后果：无法区分“本来没有数据”和“数据库故障导致未执行删除”，用户可能误以为已清理。这里不同于删除整个 AI 通道：后者已有明确的失败保留和重试机制。
- 修复：用明确的存储不可用异常/结果表达失败，接口返回 503；只有数据库确认执行成功后才返回实际删除数量。

#### MDB-02 · P2：历史删除没有与待重试/待重放任务协调，旧记录可能复活

- 位置：`ai-service/src/output/snapshot_store.cpp:1143-1212,1278-1332,1778-1880`。
- 代码链：WriteBatch 使用固定 ObjectId 的 upsert；写入部分成功或应答丢失后整批重试，pending 也会重放。DeleteOne/DeleteRange/Clear 只删 Mongo 文档，不取消 retry、ahead、queue、pending，也没有删除墓碑。history_mutex 仅串行当前数据库操作，不能取消后续重试。
- 触发例：部分写入成功后批次报错，用户删除其中已经可见的记录；同一批重试后 upsert 将该 ObjectId 再次插入。按时间删除/清空时，旧积压也可稍后补写。这里指已删除旧记录，不是清空后新产生的识别结果。
- 修复：为删除建立序列化边界，单条使用删除墓碑、区间使用删除范围/归档代次，并在写入和重放时检查；清理匹配待写任务，确保重启后仍遵守删除决定。保持整个通道删除的先停写后删库路径。
