## 结论

本次确认两个优先修复问题：统计派生写入会阻断告警消费者、停留事实丢失模型类别版本。还确认长停留导致热度截断，以及刷新和方向名称的不一致。

## 可定位的问题

### F1 · P1：派生统计写入故障会阻断原告警处理

位置：`alarm-service/src/ingestion.mjs:110`、`:126`；`dwell-visits.mjs:145`；`region-heat.mjs:84`。

`finish()` 首先等待停留事实逐条写入，之后才写行为、告警和覆盖；热度写入也必须成功才能提交 checkpoint。派生集合写入异常没有独立降级或有界失败处理，下次消费还会先重放同一 pending。持续失败会使该通道停在同一 offset；慢写也会拉长主链路。

隔离复现：让派生集合的 `updateOne()` 抛错，调用真实 `ObservationConsumer.finish()`；结果告警步骤执行 0 次、checkpoint 执行 0 次。证明的是故障条件下的控制流，不是宣称现场已经发生同类故障。

建议：在现有消费者及 checkpoint 协议中实现有界派生写入、持久化缺口状态和可恢复策略。不能简单吞异常造成假完整，也不需要增加 Kafka、另一套采集服务或推理链。验收必须覆盖派生集合持续错误／超时，且基础告警仍能前进。

### F2 · P1：停留统计没有保留模型类别语义

位置：`alarm-service/src/dwell-visits.mjs:120`；`dwell-query.mjs:43`、`:53`；前端 `DwellPanel.tsx:64` 附近及 `Analytics/index.tsx:270`。

采集时校验规则与帧的 `label_map_version`，但落地停留事实未保存该版本；查询仅按 `label_id` 过滤，也不返回版本分组。UI 用当前计数器的名称解释历史类别。若模型 A 与 B 都使用 `class:0`、含义不同，历史记录会被合并并显示为当前名称。不同区域／来源几何版本的停留也缺少热度面板已有的分组选择。

隔离复现：两个不同类别版本、不同 session、相同 `class:0` 各产生 100ms 事实；两条事实的类别版本均不存在，查询返回合并 200ms。

建议：扩展原停留事实增加来源／类别版本，查询按兼容语义分组；无版本旧数据进入未知组，不能追溯赋予当前名称。复用热度模块已有版本契约，不另建一份类别目录。

另一个需一并处理的入口：`Analytics/index.tsx:26` 的多计数器兼容签名只比较类别 ID、方式、输出和方向名，不证明相同类别 ID 在各绑定模型下同义。

### F3 · P2：停留存储上限错误地限制了持续热度累计

位置：`alarm-service/src/dwell-visits.mjs:98-115`；`region-heat.mjs:74-78`。

一个 visit 达到一小时或 128 个观测区间后被 `_blocked`，后续真实观测走 `continue`，不会调用 `onPair`。真实热度复用该回调，因此也停止增加。限制长 visit 的持久化大小是合理的，但分钟热度本身已定长、有上限，没有必要停止后续真实相邻观测累计。

隔离复现：连续 3605 秒有效检测，热度总计停在 3600 秒；一小时后新增封存热度为 0，目标 `_blocked=true`，最后一帧 issues 为空。异常只在触发时出现，缺口只记 1ms，不足以描述此后持续漏计。

建议：仍在同一次目标遍历中保留最小相邻观测状态，热度独立于 visit 持久化配额继续累计；若主动停采，则持久保存完整缺口起止及明确状态。无需重复检测或额外消费者。

### F4 · P2：“刷新”没有刷新全部数据来源

位置：前端 `Analytics/index.tsx:80`、`:100-107`、`:226`。

计数器目录只在挂载时加载。告警 effect 依赖位置与 from/to 字符串，没有 revision；对“昨天”或固定自选历史范围，点击刷新不会重新查询告警。结果是流量重新加载、告警仍旧；配置在别处修改后，筛选目录和名称仍可能陈旧。

这是静态依赖分析确认的问题，本轮没有人为修改生产告警来制造变化。

建议：同一刷新代次贯穿目录、流量、告警、规律和用户主动分析；更新目录时保留合法选择，对失效选择明确提示。为固定历史范围补刷新测试。

### F5 · P2：方向名称没有贯穿所有图表

位置：前端 `Analytics/index.tsx:146`、`:168-169`、`:247-252`。

地图和记录使用计数器自定义方向名，但 KPI、趋势、明细列仍写死“进入／离开”。计数器若定义“上船／下船”或“A→B／B→A”，同一份数据在不同位置被赋予不同业务含义；单向计数器仍占用离开指标位。

建议：复用所选兼容计数器方向契约生成所有名称；无法证明语义一致时禁止汇总。已有记录抽屉可继续复用。

## 数据口径判断

| 项目 | 判断 | 应保持的边界 |
|---|---|---|
| 通行次数 | 基于既有通行完成事实、绑定及方向历史查询，方向正确 | 是人次／车次，不是跨镜头独立人数；多位置相加可能重复 |
| 覆盖率 | 合并真实覆盖区间，并和已证明适用的配置时段取交集，合理 | 宽限不补成真实时长；历史不全显示未知；不等于识别准确率 |
| 同期比较 | 覆盖不足不计算变化率、基期零特殊处理，合理 | 当前功能会因样本不足不可用，这是数据条件，不应伪造同比 |
| 四周规律 | 最近四个完整自然周，按完整小时样本求平均，合理 | 不是总量，不是预测；无样本显示未知；需积累现场数据 |
| 告警数 | processor×zone 配对过滤，单告警文档不因多阶段重复累计，合理 | 不代表所有通行对应的异常；告警本身可有其他类别规则 |
| 停留 | 相邻真实且合格检测间隔之和，排除预测／短暂丢失时间，合理 | 观测时长下限、片段数量；F2 修复前历史类别含义不可靠 |
| 原画面热度 | 16×9、前一个观测锚点分配目标毫秒、跨分钟守恒，数学上自洽 | 逐格位置是采样估计，不是精确驻留或平方米密度；F3 会截断 |
| 平面图热度 | 计数在人工摆放中心高斯扩散，再归一化 | 属于示意，不是原画面网格投影；修改框大小也会改变视觉扩散 |
| 画面版本 | 热度按来源、几何、区域、类别版本分组，兼容会话可加时长，合理 | 会话之间不拼接目标身份／时间间隔；未知旧类别单独展示 |

真实采集覆盖与准确率仍是两件事。要验算法准确率，需使用有人工进出、停留和遮挡标注的视频，逐条核验重复计数、漏计、重启、模型切换和跨零点边界。

## UI 与功能成熟度

目前可用：统一筛选、时间预设、总览／客流／热区／规律、趋势到记录入口、告警联动、CSV、服务器平面图版本冲突机制、编辑与展示预览。底图与独立层使用同一坐标变换，编辑不改变布防范围，方向符合用户约定。

仍需改进：

1. **真实热度缺现场背景。** `RegionHeatPanel.tsx:149` 的 SVG 只有网格，没有同一几何版本背景。复用已有截图／录像帧能力提供背景并校验版本；没有匹配背景时明确提示，不能拿最新画面冒充历史。平面图叠加真实网格需要显式映射／标定，不能直接把源画面拉伸到任意规划框。
2. **选择重复。** 已选一个统计位置，进入热区后还要在“停留位置”重选，再切“画面热度”，再查询；左侧选热区也不联动右侧。建议一次选择驱动图、排名与详情，多位置时保留明确选择。
3. **解释比数据更占空间。** 总览已恢复紧凑样式，但真实热度 pane 的按钮、说明、范围、版本选择挤占图面；1366×768 必须内部滚动。保留一条关键质量提示，详细口径进入说明，热图和读数优先。
4. **更新时间不醒目。** 本轮查询截止 21:54，真实热度返回 checkpoint 20:48:21，更新时间在面板底部。应在图标题旁同时给出数据更新时间和陈旧提示。此观察不等于诊断出停采原因。
5. **能力边界仍有限。** API 最长 31 天；没有年报、完整同比、定时报表、保存报表模板、图像／PDF 报告导出；停留页面未展示后端已有的桶和阈值分布。

1. 先修 F1/F2，建立派生故障隔离和统一版本口径；再修 F3/F4/F5。继续现有技术栈、原消费者和事实集合。

5. 用同一组真实任务验收：选位置→看趋势→解释热点→找到证据→导出报告；再测多位置、模型切换、断流、低覆盖和长停留。指标是错误率、完成步骤和耗时，不凭图表数量判定超越。
