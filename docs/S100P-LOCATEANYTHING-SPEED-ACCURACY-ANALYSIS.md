# LocateAnything-3B 速度瓶颈与提速路线（2026-10-17）

本次只读分析加一个纯 CPU 原型，不调用 BPU，也没有改现网、编译或配置。

文中按依据分四类标注：
- **【官方】**：官方文档或官方源码
- **【实测】**：本板实测
- **【推算】**：按规格计算
- **【待验证】**：假设，尚未验证

## 1. BPU "占用率低"是怎么回事

- 【官方/实测】驱动 ratio 统计的是 BPU 忙碌时间占比，不是 MAC 利用率。
  - 现网 10 秒采一帧，每帧处理约 2.0 秒，其余 8 秒空闲，所以均值是 14.7–17.3%（v198、hrut）。
  - 连续推理时实测 82.5%，峰值 100%（v262）。
  - BPU 并不闲，是采集间隔让它在大部分时间里没活干。
- 【推算】逐词解码是 batch=1：每个 token 要把约 3.5GB 的 W8 权重读一遍，但只算约 6 GFLOP，算术强度约 2 op/byte。
  - S100P 内存是 LPDDR5 96bit、6400MT/s，理论峰值约 76.8GB/s（按公开规格计算，厂商没有直接给出带宽数字）。
  - 要把 128 TOPS 喂满，需要约 1700 op/byte，所以解码阶段整体的 MAC 利用率在 roofline 上只有千分之一量级。
  - 【实测，含义未完全确认】hbdk4-perf 对单个 AR1 9 层组给出过"计算单元利用率均值 31.19%"。这是工具对设备内部单元的统计，统计口径官方没写明，所以不能拿它和上面的 roofline 值直接比。
  - 【实测】hrut 读到 BPU 的 DDR 峰值约 56.8GB/s。结论：瓶颈是 DDR 带宽，不是算力。

## 2. 现网一次请求的时间构成（v143/v144：AI 暂停的私有进程，和官方基准口径一致；之后只优化了 prefill）

| 阶段 | 耗时 | 依据 |
|---|---|---|
| 首 token（视觉 27 块 + 4 组 prefill256） | 1.23 秒（v7）。第三组装上后约 1.12 秒，第四组装上后预计约 1.0 秒 | 【实测】v144、v213 |
| 其中视觉（约 29 次调用 × 14ms） | 约 0.42 秒 | 【实测】v144；**视觉块全部是 opt=0 编译**（构建脚本 build_..._moonvit_block_probe_v3.py） |
| 每个解码 token | 约 129ms（7.7 token/s） | 【实测】见下一节 |
| 典型"大门"帧（约 7 token） | p50 约 2.0 秒，其中首 token 约占 55–60% | 【实测】v279 |

逐词 129ms 的拆分（v144，1861 次调用）：
- 4 组 AR：BPU 设备时间约 89.7ms。【实测】hwperf 单组 22.4ms、每次 DDR 读 791MB，约 35GB/s。这是在生产并行时的单次诊断值，不是独占测得。
- 词表头 + embedding：约 13ms。
- 每次调用的提交/等待开销：约 4.5ms。
- Python 包装与校验：约 6ms。
- KV 准备/提交/选 token：约 14ms。
- 拷入拷出 + cache 刷新：约 3.5ms。

## 3. 官方对照（同维度）

- 【官方源码】官方 Qwen2.5-Omni-3B 和我们共用 leap_llm 里的 `Qwen2_5OmniDecoderLayer` 与 `FakeQuantLinear`（W8/A16、high_precision_qpp）。维度也一样：36 层、2048、11008、16/2 头。
  - 不同在图的划分：`Qwen2_5OmniThinkerTextModel.compile` 只编 text_model_prefill 和 text_model_decode 两张图，每个 token 提交一次（36 层 + norm + lm_head 全在一张图里）。
  - 我们是 4 组 AR 加单独的词表头，每个 token 要 5–6 次调用。
  - 默认编译参数：opt2 / balance100（oellm_build.py 里的 DEFAULT_COMPILE_KWARGS）。
- 【实测】官方 SDK 在本板上暂停 AI 时 decode 是 12.05/12.12 TPS，约 83ms/token。这已经包含官方运行时开销，而且 cache 是 2048（我们是 512）。所以官方合图的设备时间 ≤83ms，我们是约 100ms。官方页面写的是 14.03 TPS。
- 【官方】DeepSeek-1.5B 上 q4 和 q8 分别是 39.49 和 27.08 TPS，Q4 约快 1.46 倍；7B q8 6.7 TPS，折合有效带宽约 51GB/s。
- 结论：解码从 129ms 降到 ≤83ms（约 1.5 倍）有同维度实测作为依据。但对典型 7 token 的帧，这只能省约 0.3 秒，约 15%。

## 4. 本次原型实测

- 【实测】bench_locateanything_kv_inplace_v282.py，结果在 test/results/locateanything-kv-inplace-cpu-bench-v282.json。
  - 做法：KV 放在常驻的右对齐窗口里原地移位，只对新增行做 isfinite 校验。
  - 70 步 × 22 个数组，与现网 routing 的输出逐字节一致（0 处不一致），最终 cache 也一致。
  - 每组每步 CPU 时间从 3.0–4.4ms 降到 2.3–3.2ms，只省约 1.3ms/组，折合约 5ms/token（4%）。
  - 结论：Python 端 KV 处理不是主要矛盾，不值得单独做一次上线，等合图时一起改。
  - 剩下的开销来自每个 token 要整窗移动约 9.4MB/组，以及把它拷进 ION 再刷 cache。要去掉这部分，KV 得改成只追加的布局，需要先做 BPU 级的等价验证。【待验证】

## 5. 推荐路线（按投入产出比；每一步都走既有流程：同 BC → 组件逐位比对 → 完整 160 → 整图 A/B → 事务安装）

1. **视觉 27 块同 BC O2**
   - converted.bc 还在容器 /opt/locate-official-moonvit-block*-w8-v3 里，不需要重新校准。
   - 参考：prefill 组件 O2 实测快约 2.0 倍，YOLO 3.2 倍，GPEN 5.67 倍。
   - 【待验证】视觉 0.42 秒预计能省 0.15–0.25 秒，约占典型帧的 10%。
   - 风险最低，排在第四组流水线（v207→v253）之后，不和它抢编译资源。
2. **prefill chunk 改小**
   - 【官方】oellm_build 的 chunk_size 取值范围是 [128, 2048]。
   - 现网 prompt 约 128 个图像 token + 几十个文本 token，256 里约三分之一是填充。
   - 改成 192 预计 prefill 省约 25%。【待验证】需要统计 prompt 实际长度的分布，新编一个 profile，并完整 160 回归。
3. **解码按官方结构合图**
   - 36 层 + norm + 头合成一张 AR1 图；KV 改由原生代码常驻管理，第 4 节的 CPU 优化一并做进去。
   - 目标是向 ≤83ms/token 靠拢。
   - 代价最大：36 层 O2 编译耗时长、内存大，图边界变了也不保证逐位一致。适合长输出（多框）的场景。
4. **W4（官方 Q4 路线）**
   - 依据是官方 1.5B 上快 1.46 倍。但之前 W4 MLP 的 O0 只有 P 24%，失败了，只能作为研究项。
5. **"把算力用满"只能靠吞吐，不是单张延迟**
   - 采集间隔从 10 秒改到约 2.5 秒，BPU 忙碌约 80%。这是用户配置，要用户决定。
   - 多路/多帧做 batch，共享一次权重读取：【官方源码】builder 注明"TODO: 不支持 batch"，要自研，未验证。
   - 已否决：MTP/投机解码（93/160 无效）、AR balance=2（0.989 倍）、缓存工作区（只省 8ms）。

典型帧粗估【待验证】：
- 现在 2.0 秒，第四组装上后约 1.9 秒。
- 加上第 1、2 步，约 1.6 秒。
- 再加第 3 步，约 1.3 秒。

## 7. "把 BPU 用满"的边界（2026-10-18 实测 + 官方依据）

- 【实测】大门通道 2 秒一帧（0.5fps，自适应）：实际 0.498fps，BPU 均值约 65%，0 错误、0 归档反压。占用率 = 帧率 × 每帧 BPU 时间（约 1.3 秒），这个帧率下的活已经全部算完了。
- 【官方】D-Robotics LLM S100 1.0.0 API 文档（xlm_infer_async 的输入结构体）原文写着："单条推理请求的结构体。（后续会支持同时输入多条请求）"。也就是说，官方运行时目前同样是单请求串行。
- 【官方头文件】/usr/include/hobot/hb_ucp.h：hbUCPSubmitTask 支持按优先级排队；S100P 只有 1 个核。多个请求可以在 UCP 层排队，让 CPU 和 BPU 的工作互相重叠。
- 【推算，待实测】两请求重叠可以把串行时约 82% 的上限提到 90% 以上，吞吐大约多 15%，前提是负载超过单路能力（约 0.6fps）。在 0.5fps 下没有收益。MAC 利用率仍然受 DDR 带宽限制。
- 【实测 v292】视觉 O2 整链连续满载（现网并行运行）：单线程时 BPU 平均占用 97.0%，2.25 链/秒；两线程、各用一个运行时实例时 96.7%，2.27 链/秒；92 次整链输出逐字节一致。结论：
  - 只要工作量够，BPU 的时间占用就能接近满载。
  - 两请求重叠拿不到额外吞吐，所以这条路线不值得再做。
  - 现网 65% 的占用率，完全是 2 秒一帧这个负载决定的。
  - 剩下要提速，只能减少每帧的工作量：prefill 缩短、解码合图、W4。
- 【实测 v293】现网大门通道改为 1 秒目标（自适应满载），保留运行：实际 0.569fps，10 分钟内 BPU 平均 77.5%，每个采样点都在 77–78%；0 错误、0 归档反压、0 SEI 迟到；推理 p50 1.64 秒，p95 2.04 秒。
- 更正：v292 是视觉整链测试，视觉几乎全是 BPU 计算，所以它不能说明生成阶段两请求重叠没有收益。现网满载时剩下约 22% 的空档，就是生成阶段 token 之间的 CPU 时间，两请求重叠正好能填这一块。另起会话研究（不改现网）。
- 【官方】RDK Python API（hbm_runtime）文档：推理时在 C++ 内释放 GIL，"multiple Python threads can issue inference calls simultaneously"；收益"depends on BPU core count"（S100P 只有 1 个核）。
- 【实测 v294】按生成阶段节奏做原型：每步 4 次（现网 routing 准备 KV → AR1 组 → 提交 KV），官方 hbm_runtime 单实例，现网临时降到 0.1fps、结束在 finally 恢复 1fps。
  - 单流：7.58 步/秒，BPU 81.5%。
  - 双流：7.42 步/秒（0.98 倍），BPU 84.2%。
  - 输出逐字节一致。
- 结论：两请求重叠在生成阶段同样拿不到额外吞吐（视觉 v292 也是如此）。占用率读数约 80% 时，BPU 的实际处理能力已经到顶，剩下的读数空档不是可用算力。现网 1 秒自适应满载（0.569fps，77.5%）已经把 BPU 用满。
  - 要再提速，只能减少每帧的工作量：prefill 缩短、解码合图、W4。

## 8. 高精度版本研究（2026-10-18，现网 v11 保持不动）

- 视觉注意力配方单块探针（v296，block5，编译器精确仿真，与原版 BF16 的 rel_L2）：

  | 配方 | rel_L2 |
  |---|---|
  | 现网 qk8×8 | 0.00665 |
  | qk8×16 | 0.00613 |
  | qk16×16 + sv16×16 | 0.00503（全 BPU） |
  | 再加 16bit 权重 | 0.00368，但单块 HBM 190MB，27 块约 5.1GB，装不下 |

- 27 块 qk16/sv16 全部构建成功，全 BPU，逐块误差降 4–39%。
  - 板端特征采集 v297：现网对照与 v1 存档逐字节一致。
  - 旧 72 项 + BF16 文字：P/R 从 64.7 升到 72.9/75.0，但拥挤 4K 单图从 52.6 降到 18.4。
  - **全 BPU 独立 160（v301）：P/R 57.1/62.1，基线 59.3/62.6，有 2 项新增未结束 → 不采用。**
- 独立 160 归因（v303，两次原生接口正控逐字一致；同一套计分重算基线，得到 137/231/219 与官方完全一致）：

  | 组合 | IoU≥0.9 | IoU≥0.5 |
  |---|---|---|
  | 现网 BPU 视觉 + BF16 文字 | 68.1/66.2 | 90.6/88.1 |
  | 现网全 BPU | 59.3/62.6 | 75.3/79.5 |
  | 候选视觉 + BF16 文字 | 67.5/61.6 | 88.0/80.4 |

- 结论：
  - 现网的 P/R 是与原版 BF16 在 IoU≥0.9 下的一致率，不是对真实标注的准确率。按实用标准 IoU≥0.5，全 BPU 约为 75/80。
  - 在 IoU≥0.5 下，最大损失来自 **W8 文字解码**（90.6→75.3）。
  - 解码组的注意力早已是 A16（构建脚本 v3 第 37–39 行），所以剩余误差主要来自逐行 W8 权重。
  - 历史 PC 逻辑配方"校准 INT8 group32 + 5% INT16"在旧 72 项上达到 88%（视觉为 BF16）。下一步先在 PC 上用 BPU 视觉特征仿真"逐行 W8 对比 group32 INT8"的文字解码，确认能补回多少，再决定是否投入 BPU 分组量化工程。
- 不可行：
  - 历史 FP32 视觉（3 路 INT8 分支），每块 367MB，27 块约 9.9GB；
  - 视觉 W16，每块 190MB。
