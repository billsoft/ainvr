# 通道增长与内存准入设计

## 产品约束

沿用现有 C++ AI、Python 录像、SRS、控制台与配置中心，不增加独立资源调度服务或第二套存储。目标是可解释的容量拒绝、明确的运行时压力状态和可恢复的故障；不得通过降低证据分辨率、丢弃告警原图或 CPU 推理回退实现容量目标。没有实际多路验收前，不公布可承载路数。

## 硬件与记账边界

.190 为 S100、12GB 总物理内存、约7GB ION；Linux MemTotal 约4.31GiB。内存控制器使用 cgroup v1，不能按 v2 MemoryHigh 的行为部署。.189 为另一容量档，不能沿用 .190 的具体预算。模型权重共享只消除同模型重复常驻，解码、GPU、逐路缓冲仍随通道增长。

区分四类数据：部署预算、已承诺预留、实际进程/cgroup占用、系统 MemAvailable。不得把完整部署预算再与已扣除当前占用的 MemAvailable 相加比较；不得将 tmpfs 占用与已经包含它的 cgroup 统计重复求和。受控缓冲上限不是进程RSS或整机硬上界，SDK/驱动、线程、传输和内存分配器余量必须另留。

## 分区与权威准入

使用服务级固定额度分区，不让 AI 和录像同时争抢一份通过健康接口读取的可用额度。健康接口只提供预检，不构成资源锁。最终准入在资源所有者内部原子执行：AI 使用共享池和 RAII 票据；录像复用现有 supervisor 串行锁、在途退役及 orphan 记账；SRS 保留容器和 tmpfs 上限及 HLS 独立进程。

AI 创建和启用配置在持有配置变更锁时检查编码缓冲承诺总量；运行时构造缓冲再次原子申请，退役对象仍持有票据，防止重启交叠重复分配。拒绝发生在落配置之前时返回明确的容量错误；退役未完成导致的运行时拒绝保留已保存配置与错误状态，按现有退避恢复。禁用、删除及纠正超配必须可进行，不能把存量超配变成无法修复的死锁。

录像额度为部署配置，启动时校验，健康接口分别暴露全局缓冲预算、运行及退役预留和实际队列；子进程常驻不计入GOP缓冲，而在进程/cgroup实际观测中显示。不得因多建一路把已有管线已承诺的额度重新当作空闲。

## 编码包与证据策略

编码包每通道保持时间、帧数、字节三种限制，保留关键帧重同步、DROPPED不扩延迟和PTS/会话隔离。常规模型的内存额度可配置；慢模型现有 AuSpool 仍使用 SSD，内存包与磁盘保留量分别记账。单包超过上限在入队前明确拒绝，不能依靠入队后短暂超量来维持名义上限。

归档384MiB池、审核原图像素池、持久交付和证据ACK顺序不缩减。当前存在实际整帧下载，不能按典型目标ROI直接降低整帧预留。新来源/分辨率变化的归档准入继续在实际分配前执行。

## 用户操作

新增、启用或增加资源需求：预检失败说明哪个服务、预算、所需额度和当前承诺。用户可以停用其他通道、明确关闭不需要的输出，或者调整部署预算；不静默改变画质。停止后资源可能仍在安全收尾，状态必须区分运行和退役；不能在尚未释放时报告可用。

保持现有控制台接口转发及错误显示，不引入第二套通道创建流程。运行健康接口提供结构化 memory 字段，供现有状态页和诊断使用；界面显示的预算不能冒充整机可承载通道数。

## 交付验证

单测覆盖并发申请、额度耗尽、释放、构造失败回滚、退役仍占额度、超大包、PTS/关键帧/延迟语义与录像预算边界。部署采用 SSD 构建和回滚；维护窗口暂停依赖服务与数据库，等待数据库健康后恢复。线上核对实际配置、预算、服务状态、录像连续性、告警证据及审核。

多路容量认证单独记录真实源分辨率、码率、GOP、运行模型和推理FPS，包含启动峰值、重连、密集截图、磁盘变慢与24小时稳定性。未完成这些场景时，不宣称绝对无OOM、不声称4K/8K容量已认证，不把模拟流当真实摄像头验收。


## 本次 .190 部署容量档

- 活动 AI 通道名额：2（`AINVR_AI_ACTIVE_CHANNELS=2`）。无输出的 AI 通道也必须申请；保留名额直至捕获/推理线程结束。配置承诺包含所有 enabled 且未删除的通道，手工停止不会自动撤销启用承诺；需要释放配置名额时应停用。
- 编码缓冲：全局192MiB、常规每路96MiB（`AINVR_AI_AU_TOTAL_MIB=192`、`AINVR_AI_AU_CHANNEL_MIB=96`）。默认源码为384MiB/96MiB；未知部署应显式选择配置档。慢模型 SSD 保留量不计为常驻包内存，但仍占通道及保守缓冲额度。
- 录像 GOP 缓冲：256MiB（`AINVR_RECORDER_BUFFER_MIB=256`），源码兼容默认1536MiB。保留现有码率权重、在途收尾、孤儿进程与GOP恢复机制。
- SRS沿用768MiB容器和384MiB tmpfs；Mongo沿用1GiB容器。没有更改HLS和告警证据策略，没有给 cgroup v1 套用 MemoryHigh。
- 此档是保守的运行保护配置，不等于“最大支持两路”，也不是每路CPU内存已被完整计量。通过实际双通道与超额拒绝验证后上线；更多路数和4K/8K容量需要另行压力认证。
