# 告警与设防区域评审：核实结论与修复清单（2026-10-20）

需求目标：在 AI 监控画面上设防区域，按"检测什么目标、发生什么行为"建触发器：

| 行为 | 典型场景 | 判定依据 |
|---|---|---|
| 出现 | 火情、烟雾、指定物体出现 | 全画面或区域内检测到标签并持续满时长 |
| 接近 | 坠落区、危险边缘 | 位置点在区域外、距边界不超过接近范围 |
| 接触 / 侵入 | 禁区 | 接触=检测框与区域相交；侵入=位置点从区域外进入区域内 |
| 穿越 | 通道计数 | 从一条边进入、另一条边离开 |
| 越线 | 门口进出计数 | 位置点按方向跨过一条线 |

只记录所选触发器（标签 × 行为 × 区域 × 生效时段）产生的行为记录；"记录并告警"才生成告警。

## 三、仍需注意的隐藏条件（文档化，不改代码）

- **部署即改变判定口径**：区域内出现、穿越须换边、侵入重新触发三项对已启用规则立即生效，规则版本号不变；部署前后的统计不可直接比较。部署顺序：告警服务先于控制台后端（后端会下发新字段 `appearance_mode`、越线 `direction`）。
- **断流显示未做**：告警的 `last_seen_at` 只在新阶段时更新，不是逐帧心跳，不能用来判断"观测中断"（否则长时间站在禁区里的人会被误标）。正确依据是通道级的最近消费观测时间，需告警服务按通道暴露后再在列表中显示。
- **"按有无"出现的输入前提**：仍需开启目标跟踪（启用门槛不变）；只有被跟踪器接纳为轨迹（含未确认）的检测才进入观测日志，低分检测（编号为 0）和低置信显示框都不参与。这类告警不并入单个目标的活动，列表中直接显示"已结束"。

- 规则触发次数、跟踪目标数、实际人数是不同指标；多条规则的次数不能相加当客流。
- 丢失保留默认 3 秒：AI 采样间隔大于它时，持续时间与穿越状态会不断重置；稀疏采样看不到完整穿越。
- 推算框、低置信框不能作为越界证据；缺帧不能证明目标离开。
- 修改区域后，已启用规则仍使用冻结版本，需要重新确认保存规则。
- 火情须先有能输出对应标签的模型；位置参考建议用检测框中心。
- 观测日志在推理线程同步落盘的性能风险、密钥轮换残留旧记录，留给后续专项。

## 五、触发器重构（2026-10-20 下午，交互稿已定稿；未部署、未提交）

交互设计稿：https://claude.ai/artifact/Rv7Cegea3N4x9sYcAbddAu 。已确认的决定：先报再升级；同一通道同一目标跨触发器合并；在热区上点边选方向，可不限；接近距离在画面上拖动（原始画面像素）。

**需求规则**
- 告警只来自触发器。一个触发器只检测一种行为（出现、接近、碰撞侵入、穿过），可以覆盖多个通道。
- 出现按全画面判断，不需要热区；另外三种必须为每个通道选热区，没有热区、未开跟踪或模型里没有所选目标的通道不能选。
- 目标身份是"编号 + 名称"：不同模型的同一编号可能是不同目标（`class:0` 可能是人员也可能是火焰），名称不一致的通道不能选，前后端都校验。
- 出现按跟踪编号持续计时：从第一次真实检出开始；真实检出、低置信框、带推算框的补帧都算连续；没有推算的丢失帧、或超过帧间隔自适应上限（max(1.5 秒, 4×实测帧间隔)）的停顿会重新计时；只在真实检出帧上触发（保证有截图证据）。
- 方向 = 热区的边：侵入取被跨过的边，穿过取进入边和离开边，接近取最近的边；不选边即不限方向。推算框和低置信框不能证明越界。
- 告警：同一通道同一编号一条活动，跨所有触发器；命中更高级别时原地升级，并显示达到该级别的触发器和热区。活动在编号从跟踪器消失、触发器集合变化或布防时段切换时结束。统计按触发器逐条记录，不受合并影响。
- 删除：越线计数、接触、出现的"按有无"口径、按角度的方向过滤（`docs/ALARM-DIRECTION-POLICY.md` 已被本节取代）。

**数据与接口**
- 参数库新表 `alarm_triggers` / `alarm_trigger_versions`（迁移 `005_alarm_triggers.sql`）。旧监控规则按行为拆成触发器（编号沿用旧规则编号 `monitor:behavior`，历史统计仍可归属），接触和越线不迁移，方向重置为不限，接近距离按画面宽度换算成像素；迁移后配置版本加一。
- 接口：`GET/POST /alarms/triggers`、`POST /alarms/triggers/:id/state`、`POST /alarms/triggers/synchronize`；`GET /alarms/sources/:id` 不变。旧 `/alarms/monitors` 已删除。
- 下发规则：每个启用触发器的每个通道一条，编号 `触发器@通道`，携带 `trigger_id`、`entry_edges`/`exit_edges`、`approach_px`。
- 行为记录新增 `trigger_id`、`engine_semantics=2026-10-20.triggers`；统计与记录查询支持 `trigger_id` 筛选和"按触发器"分组，旧记录按规则编号兜底。

**部署顺序（强耦合）**：告警服务先上、控制台后端紧接着上、前端最后。新后端启动即执行迁移并下发新格式规则，旧告警服务不认识这些规则。新告警服务能接住旧格式快照（读不懂的旧规则按"不同规则"处理）。部署后口径变化：已启用的旧规则会以新口径运行。

帧率自适应：按最近 8 个帧间隔的中位数判断中断（停顿 > max(1.5 秒, 4×中位数)），长间隔也计入，所以一开始就低帧率或中途长期降帧的通道几帧内就能恢复判定。

**测试**：告警服务 96 通过 / 2 跳过（需原生构建）；后端 340 通过，PG 集成 3 项在独立库通过；前端 119 个文件 978 项通过。
