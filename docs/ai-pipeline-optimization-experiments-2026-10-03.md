## 1. 结论与范围

优先优化 **截图归档的取图方式**，其次研究 **NVMM/EGL 映射生命周期**。目前没有证据支持重写整个推理管线、增加一批线程、重写归一化 kernel，或承诺增加一路 8K AI 通道。

本次得到一个有明确收益且初步保持像素一致的候选：**根据全景采样映射计算所需原图区域，只下载该区域，继续使用原来的 CPU remap 和 resize。** 六组测试的像素最大差异均为 0。它还不是经过完整业务验收的生产实现。

## 3. 试验方法与隔离

1. 所有试验程序、对象文件和日志放在 `/home/sunrise/ainvr/.codex-review-cache/ai-perf-20261003/`。未重新链接或覆盖生产二进制。
2. 暂停生产 AI，核实 MainPID=0；授权执行器只管理 SRS，不会自动启动本试验暂停的 AI。
3. 保留 SRS、源流录像、授权和数据库。试验程序不发布 AI 输出、不写识别数据库。
4. 首次从真实相机取一帧，固化为同一份 RGBA 样本；后续所有组件对照读取相同样本。实时解码场景有单独线程持续取帧，避免堵住解码队列。
5. 当前对象文件与 `-O2` 重编译的相关 C++ 模块做 A/B/B/A 对照。CUDA kernel、TensorRT engine、OpenCV 库保持相同。这不是完整 Release 服务的部署验收。
6. 每轮先预热 8 次；预处理+推理每组 80 次、交替顺序重复 3 轮；其余项目 30–100 次。ROI 截图六组各交替 20 次。
7. 每个进程有超时，控制脚本 finally 恢复生产 AI；监测 tegrastats。两次暂停约为 16:29:08–16:31:59、16:32:27–16:33:09，均为本次主动试验。
8. 两次恢复间没有部署新代码；试验期间的 AI 输出/识别/输出录像空隙属于计划内停服。相机源流连接未改变。

### 必须保留的测量边界

- 这是组件级试验，不包含完整的发布、GPEN、数据库归档及实际 15 FPS 调度。不能把试验约 34ms 与生产约 42ms 的推理耗时差异当成优化收益。
- 频率动态变化，温度最高约 79.4℃；背景服务持续工作。单次不到 3% 的差异不足以决定生产改动。
- 最早 `production-before.json` 采样与独立试验构建部分重叠，不用于收益对比。最终生产基线在编译与试验退出后重新采集。
- 首次 decode-off 试验可能受补充试验编译影响，因此追加无编译的 `off2` 复测；解码关闭后整体推理未出现数量级改善。
- 固定帧、有限框位置无法证明所有图像、所有框数量、重连以及长期生命周期均正确。
- 首版 GPU 截图差异统计中的 mean_abs_error 是第一个颜色通道均值；max_abs_error 覆盖所有通道，PSNR 使用完整图像。

### 保持原 CPU 算法、只下载需要的 ERP 区域

计算原映射表的 min/max，加上 cubic 插值邻域，裁成有效源图矩形；下载该矩形，将映射坐标减去矩形起点，再执行原来的 `INTER_CUBIC + BORDER_REPLICATE` 和 resize。没有修改归一化、模型、检测框或透视几何。

## 5. 产品化重构顺序

### 第一阶段：归档取图优化（优先实施）

修改边界：`snapshot_store.hpp/.cpp`、`channel_worker.cpp`；必要时新增纯数据的截图采样计划模块。保留现有 SnapshotStore 写入线程及数据结构的业务语义。

1. 将当前“需要时取整帧”的 FrameProvider 改成按本帧检测集合请求裁剪结果的接口；保留源分辨率、检测坐标、PTS、流代数及生命周期。
2. 截图节流、启用判断、目标为空判断和队列容量检查放在昂贵下载之前。预留队列名额要覆盖异常和取消，不能提前改变现有统计语义。
3. ERP 使用**现有 ErpMapCache 的实际映射表**计算范围。不能根据原始检测框直接截取，因为透视变换会访问框外像素，接缝/极区更明显。
4. 保持 1.5 倍超采样、原插值与边界处理。普通图像分支也必须保留原 CropWithPadding 的坐标、方形框、padding、尺寸及 resize 规则。
5. 每帧多个目标一起制定计划。合并有明显重叠的下载区域；若总下载成本接近整帧，退回**复用 host 缓冲**的整帧路径，避免每个目标各下载一次整帧。
6. 设置单帧计划数、总字节、缓存字节上限；映射异常/非有限值/分辨率变化时走安全回退，不读取越界内存。
7. 第一版下载及对 CUDA 图像的访问仍由推理线程持有有效 DeviceView 完成；只把已独立拥有内存的小图交给归档线程。不得把 GpuMat 裸指针放入后台队列，也不长时间扣住解码池帧。
8. 原有亮度、增强、JPEG、MongoDB、数量配额及删除通道清理机制不变。异步增强与主推理竞争 GPU 的影响另计时，不把它归因于取图。

验收：

- 正常图像、ERP 接缝/极区、越界框、非整数框、多目标、动态分辨率的旧新截图对拍；默认要求逐像素一致，未满足时保留原路径。
- 相同固定帧、相同框、相同背景负载下，取图 p95 明显降低；多目标场景不能出现更高峰值内存或更差耗时。
- 真实相机有检测并实际归档时，确认 MongoDB 新记录、图片、框坐标与 PTS、SEI 对齐、录像均正确；观察推理周期 p95、过载计数增量。
- 覆盖断流重连、停通道、删通道、授权停止、队列满、数据库断开。不会访问已释放 NVMM，也不会无限积压。

### 第二阶段：EGL 映射生命周期试验（有依据，但不直接上缓存）

修改边界：`stream/source.hpp/.cpp`、相关帧生命周期测试。

- 先分别计时 gst map、NvBufSurfaceMapEglImage、CUDA register/get view、unregister、EGL unmap。当前约6ms是整个过程，不能全部算到预处理统计里。
- 试验在**实际底层缓冲的有效生命周期**内复用 EGL/CUDA 注册，而非按像素指针建永久全局缓存。缓存键必须能区分 GstMemory/池实例和重连代数。
- 不得为缓存长期持有整个解码池；缓冲销毁、池更换、分辨率变化时必须释放资源，析构线程的 CUDA context 必须正确。
- 用连续真实帧、反复重连/启停、不同分辨率验证是否稳定节省时间；监测句柄、CUDA资源、NVMM池与RSS。未完成这些验证前不纳入生产。

### 第三阶段：构建与诊断收口

- `deploy-package/build-release.sh` 的 AI 构建当前复用 `ai-service/build`，只设置 CUDA 架构，未固定 CMAKE_BUILD_TYPE；会继承 Debug 缓存，并直接重链接线上路径。
- 改成独立产物目录，显式 Release 或 RelWithDebInfo，记录源码版本/参数/二进制校验值；验证完成后再替换并重启。此次未修改打包脚本。
- 给 map/unmap、GPU预处理、enqueue+回读、SEI构建/加锁等待、Snapshot Offer、下载字节、ERP采样、增强排队分别计时。
- CPU墙钟与 CUDA Event 时间分开；移除同步时不能把等待“挪到下一阶段”误报成提速。日志按统计窗口和超阈值限频，避免每帧写盘。
- TensorRT 本次加载仍出现跨设备型号 engine 警告。有原始 ONNX；另安排同板独立 engine 重建及精度/性能对拍，不能覆盖当前文件后直接认定收益。

## 6. 暂不采用及未验证项

- 不重写现有融合归一化 kernel：实测只约0.47ms。
- 不优先引入 pinned 输出缓冲/多流推理：当前结果仅7200字节，尚无回读瓶颈证据。不能把离散GPU经验直接套到Jetson共享内存上。
- 不因单次快约1ms就删除同步；保持错误传播、结果可读性和帧生命周期。
- GPU全景截图保留为实验候选，当前有像素差异，不能宣称与原图像算法等价。
- JSON/SEI 仍有锁内处理，当前没测到锁等待瓶颈；只计划先增加诊断，不直接重写发布架构。
- 本次没有实测压缩发布分支优化、GPEN调度、多人密集检测、NV12直入CUDA、推理CUDA Graph、增加通道容量或INT8。不能承诺这些方向无收益，也不能承诺一定提速。
- 归档优化主要消除每5秒可能出现的尖峰，并非让每一帧都省掉70ms；不会自动把15FPS变成30FPS。
- 每路8K RGBA在30FPS下仅完整图像写入量就约3.54GB/s（内存流量，不是磁盘码率），但本次解码开/关组件对照不能推导可新增AI通道数量。容量必须在完整业务链另测。
