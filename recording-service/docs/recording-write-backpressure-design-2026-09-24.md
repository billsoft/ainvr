# 录像写入背压：GOP 对齐抛帧 + 告警（设计，2026-09-24）

## 1. 问题

- 存储能写但**写得慢**（NAS 忙、链路窄、多路 4K）时，现状是 ffmpeg 同步写文件被拖慢 →
  读 RTMP 变慢 → SRS 播放队列超过 `queue_length`（10s）→ SRS `SrsMessageQueue::shrink()`
  **清空整个队列只保留编码头，不对齐 I 帧**（已读 SRS 6.0 源码确认）。随后到达的 P 帧没有
  参考帧，录像里出现花屏段，且**完全静默**，索引与 UI 看不出。
- 连接失败 / 写入报错 / 写入完全无进展：维持既有策略——停录、熔断、自愈、明确报错（不变）。
- 附带缺陷：
  - 午夜为换日期目录重启 ffmpeg（每天一次断档）；
  - 停滞看门狗用"多久没出新分段"判断，I 帧间隔很长的流会被误判为存储卡死。

## 2. 目标

1. 写得慢：录像服务不被拖死、读流永不阻塞；**只按完整 GOP 丢**，留下的每一帧都可解码。
2. 丢了多少、何时丢的精确记录（按到达墙钟时间），并在 WebUI 明确告警。
3. 同进程内分段一帧不丢（现状已满足，重构后保持）；新增：**跨天不重启**，零断档。
4. 慢 / 卡死 / 报错三态分明：慢 = 降级继续录；卡死与报错 = 停录（沿用熔断链路）。
5. 编码无关（H.264 / H.265 同一路径）；I 帧间隔任意。

## 3. 架构：读 → GOP 缓冲闸门 → 写

```
SRS ──RTMP──> reader ffmpeg (-c copy -f mpegts pipe:1)        每通道常驻
                  │ stdout（永远及时读走，SRS 队列不积压）
                  ▼
          GopGate（录像服务进程内，asyncio）
            · TS 解析：PAT/PMT 缓存，视频 PES 起始 + RAI 标志 = I 帧边界
            · 内存缓冲：按 GOP 排队，字节上限（默认 64MB/路）
            · 满水位 → 进入丢弃态：新到 GOP 整组丢弃，直到水位回落到 50%（滞回，
              避免碎片化丢弃）；每次丢弃合并为一个"丢弃事件"
            · 分段：文件年龄 ≥ segmentSeconds 后遇到下一个 I 帧即换文件；
              丢弃事件后恢复写入时也换新文件（文件内部无时间空洞）
            · 文件名 = 该文件第一个 GOP 到达闸门的墙钟时间（精确，不受写入积压影响）；
              日目录按该时间取 → 跨天自然切换，无需重启
                  │ 每个分段一个 writer
                  ▼
        writer ffmpeg (-f mpegts -i pipe:0 -c copy [-bsf:a aac_adtstoasc]
                       -f mp4 -movflags frag_keyframe+empty_moov+default_base_moof <file>)
            · 每个 writer 的输入 = 缓存的 PAT/PMT + 从 I 帧开始的连续 GOP
            · 换文件：关旧 writer 的 stdin（它自行 flush 退出，后台有界收尸），立即起新 writer
```

实测依据（板上 ffmpeg 4.4.2，大门口 4K H.264）：
- TS 中 RAI 标志数 = ffprobe 关键帧数（4/4）；
- 在任意 I 帧处切成两段各自封装 MP4，帧数 250+251 = 源 501，首帧均为关键帧，音频正常；
- ffmpeg 4.4 的 mp4 封装不会自动转换 ADTS，必须显式加 `aac_adtstoasc`（仅当 PMT 音频为
  ADTS AAC，stream_type 0x0F）；
- Python 逐包解析 25s 4K 流耗时 0.39s（约单核 1.5%/路）。

### 实现要点（评审后收紧）

- **两级上限**：软上限（单路预算 × 0.75）在 GOP 起点整组丢弃，水位回落到软上限一半才在
  下一个 I 帧恢复；硬上限只在**帧起点**判断，单个超长 GOP 撑爆时截掉其余部分。
  单路预算 = clamp(1.5GB / 在录通道数, 32MB, 256MB)；4K≈21Mbps 时 256MB≈97s，覆盖实测约 64s
  的 NAS 卡顿。写入卡死判据 60s 小于缓冲秒数，卡死先于缓冲写满被识别为故障而非"写得慢"。
- **队列只存整帧**：正在接收的一帧扣在闸门里，下一帧起始包到达才入队；写端按批（≤1MB）
  合并写入。截断、停止时写端拿到的最后一帧也完整（真实流验收曾抓到半帧解码错误，已修）。
- **时间**：文件名与丢弃区间用 PTS 映射墙钟（锚点 = 近 5 分钟 min(到达−PTS)，33 位回绕
  展开），读端连上时 SRS gop_cache 的突发不会把首个文件名拉晚；首个文件等 2s 让锚点稳定。
  同名文件已存在则顺延 1s 并以 `-n` 兜底，绝不覆盖。
- **停止**：先停读端并给写端 5s 写完积压；超时则丢弃积压（记账为 stopped，区间止于进行中
  丢弃段起点，不重叠）并终止进程；SIGKILL 后仍有进程（读端或任一写端）未退出则整条管线
  转 orphan，spawn 围栏防双写。
- **open-GOP**：帧数守恒；切点后领头 B 帧引用上一 GOP，可能各坏 1~2 帧（监控相机普遍为
  closed GOP）。

### 验收（板上 ffmpeg 4.4.2）

- lavfi 生成源：1s GOP+B 帧、30s 长 GOP、H.265、open-GOP——各分段视频帧数之和 = 源，
  音频包守恒（首个 I 帧前少量音频除外），每文件 `-f null` 零解码错误、首帧关键帧；
- 限速写端：只按整 GOP 丢弃，写下帧数 + 丢弃时长 ≈ 源（误差 ≤1 GOP），文件全部零错误；
- 生产 4K 流 4 路并发（1 路写端限速约半码率）75s：事件循环 p50 1ms / p99 8.8ms / max 25ms，
  SRS shrink 0 次，丢弃恰为 2 个 GOP（16.67s），全部输出文件零解码错误，进程 RSS 67MB。

### 三态判定（每通道）

| 状态 | 判据 | 处理 |
|---|---|---|
| ok | 缓冲低于高水位，未丢弃 | 正常 |
| degraded（写得慢） | 近 1 小时发生过丢弃，或正处于丢弃态 | 继续录；告警；记录丢弃事件 |
| stalled（卡死） | 有待写数据但写入 **N 秒（60s）无任何字节进展**；或建日目录/起 writer 超时 | 沿用熔断：`storage.trip` → 停录 → 自愈重挂 |
| 报错 | writer 非预期退出（非我们关闭 stdin 引起）/ reader 异常退出 | 管线结束 → supervisor 退避重启；持续失败由存储探活判定停录 |

停滞判据改为**字节级写入进展**，与 I 帧间隔、分段时长无关，替换原"多久没新分段"的看门狗
（修复长 GOP 误判）。

## 4. 数据与接口

- SQLite 新表 `drop_events(channel_id, start_ts, end_ts, dropped_ms, gops, bytes)`，
  按通道 + 起始时间索引；配额轮顺带清理早于该通道最旧录像的事件。
- `GET /v1/recordings/drops?channel=&from=&to=` → 丢弃区间列表（时间轴用）。
- `/v1/recorder/channels` 每通道追加：`writeState`（ok|degraded|stalled）、`droppedMsLastHour`、
  `bufferSec`（当前积压秒数）。
- `/v1/recorder/stats` 追加：`writeDegradedChannels`、`droppedMsLastHour`（全部通道合计）。
- `/v1/recorder/health` 的 `warning` 合并写入告警，例如
  "录像存储写入速度不足：近 1 小时 2 路共丢弃约 95 秒（按完整画面组丢弃，已录画面可正常播放）"。
  仪表盘经 observability 已自动展示 `warning`。

## 5. UI 设计（放在人本来就会看的位置，不新开页面）

1. **录像回放页 · 左上存储卡片**（主位置）：容量条下方一行琥珀色
   "⚠ 写入速度不足 · 近 1 小时丢弃约 X 秒"，悬停说明
   "存储写入跟不上录像码率，已按完整画面组丢弃，保证录下的画面可正常播放；请检查 NAS 负载或网络"。
2. **录像回放页 · 时间轴**：丢弃区间画成琥珀色块（与"绿=可播放 / 红=SEI 识别"并列），
   悬停显示"写入不足丢弃 X 秒"；图例追加"琥珀：写入不足丢弃"。
3. **接入管理 · 通道录像徽标**：在录且 `writeState=degraded` 时显示"录像中 · 有丢帧"（警告色），
   详情为近 1 小时丢弃秒数；stalled 走既有"存储异常"。
4. **仪表盘 · 录像服务行**：明细显示 health.warning（已接通，无需前端改动）。

## 6. 不在本次范围

- H.265 源：本架构对编码无关（解析同时识别 H.264 0x1B / H.265 0x24），但**读端**
  ffmpeg 4.4 的 RTMP 不认 H.265。后续只需替换 reader（新版 ffmpeg 或从 SRS 拉 HTTP-TS），
  闸门与写端不动。需要真实 H.265 推流实测后决定。
- SRS `queue_length` 不改：闸门保证读端永不积压，SRS 不会再对录像连接收缩。

## 7. 取舍说明

- 为何不依赖 SRS 抛帧：不对齐 I 帧（会花屏）、静默、无法计量。
- 为何不做本机磁盘暂存：用户要求"写不过来就抛帧"，内存 GOP 缓冲即可吸收短时抖动
  （64MB≈4K 下 24s / 1080p 下约 1 分钟），且不改变"录像只落 NAS"的铁律与回放/配额/扫描路径。
- 为何每分段一个 writer 进程：分段边界、文件命名、丢弃后断开都由闸门精确控制，
  不再依赖 segment muxer 的时间判定与 strftime；ffmpeg 冷启动约百毫秒，每路每分钟一次可忽略。
